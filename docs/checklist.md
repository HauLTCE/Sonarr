## Phase 3 — Chat core ([10-elaine-engine.md](docs/10-elaine-engine.md))

### Engine skeleton (`Sonarr.Elaine`, pure)

- [/] Determinism boundary: injected `IClock` + seeded RNG (seed = logical turn); nothing ambient
- [/] Migration — `chat`: person, fact, episode, relationship_event, stance, stance_agreement, guild_state, intent_embedding
- [/] Persona v2 loader: directory-based (`sonarr.yaml`, `intents/`, `pools/`, `stances.yaml`, `overlays/`)
- [/] Persona validator: reachability, dangling refs, capture safety, pool coverage per mode, overlay collisions
- [/] Shadowing report from the validator
- [/] Fail-fast rule: invalid persona refuses to load at boot **and** at hot-reload (old file stays live)
- [/] Normalizer: case-preserving spans + style detection (CAPS, wall-of-text, emoji-flood)
- [/] Lexical matchers (keyword / regex / fuzzy) with **scored selection** — specificity + topic-affinity + guard bonuses; declared order breaks ties only
- [/] Multi-intent: primary response + side-effect acknowledgments
- [/] Activity stack (idle / rps / argument / story-scene…) — persisted in `chat.person.activity_stack`
- [/] Orthogonal mood & relationship dimensions (registers: anger, boredom, fondness, trust, grudge)
- [/] Topic stack (cap 5, recency decay)
- [/] Pending-question queue + unanswered detection
- [/] Fired-log persisted (`once:`/`cooldown:` no longer reset every message)
- [/] Composition: optional mood fragment + core line + optional callback tail
- [/] Engine returns text (+ optional emoji reaction) only — never moderates, never acts

### Persona migration

- [/] ~~Scripted~~ v1 → v2 conversion (done directly, not as a Migrator verb — a one-shot converter has no second use)
- [/] Hand-polish pass + validator clean
- [/] Persona hot-reload watcher in `Sonarr.Bot`: validate, atomic swap only if valid, log either way
- [/] Persona directory mounted as a volume (`./persona:/app/persona`)

### Pipeline & adapter (`ChatPipeline`, [08](docs/08-background-services.md#event-driven-gateway-handlers-not-timers))

- [/] Gate: mention/reply only + engagement budget (`chat:budget:{channel}`) + kill switch
- [/] Load: `chat:hot:{guild}:{user}` → Postgres fallback; write-through on save (row wins a stale snapshot)
- [/] Session state `chat:session:{guild}:{user}` (10 min sliding) — "message 6 of a back-and-forth" vs "first contact in days"
- [/] Channel ring buffer `chat:ring:{channel}` (metadata only, cap 10, 15 min) — pushed for ambient messages too; rapid-fire + two-people-talking *reads* still unused
- [/] Repeat-ping detection `chat:lastping:{guild}:{user}`
- [/] Affect engine: apology-sincerity check, thanked-reaction, register updates (`ChatAffect`)
- [/] Persist person/facts/episodes/relationship_event in **one transaction** + session keys (commit before she speaks; Redis writes after)
- [/] Deliver: typing delay ∝ length, then reply (typing indicator held for the pause)
- [/] `EditWatcher` — `chat:replied:{channel}:{msg}` hit → authored "stealth edit" call-out (`user_receipts`, no turn, no register movement)
- [/] Wall-clock signals from the adapter: absence tiers, multi-day grudge decay, 3–6 am pool, mood-of-the-day seed, seasonal overlays (`ClockSignals`; `AbsenceTier` derived but not yet read by a pool)
- [~] Worst-case budget check: ~50 ms compute on the embedding path — lexical half pinned (`TurnBudgetTests`: a full miss runs every pattern of every intent, ceiling 5 ms/turn). The embedding half is Phase 4's J2900 benchmark below.

### Commands & tests

- [/] `/relationship [user]` — authored descriptions, no numbers (`relationship_<tier>` pools; tier recomputed from trust, not read from the stored column; another user's tier is deflected, not reported)
- [/] `/memories`, `/memories forget fact` (autocomplete from your facts) — `/memories list` + `/memories forget`, both ephemeral, all four openers authored
- [/] Behavior catalog: every pinned behavior from the legacy test suite, rewritten — the regression floor (`BehaviorCatalogTests`; legacy behaviors with no v2 route — bare-number reactions, negation routing, hello counting, assigned nicknames — are recorded there as comments with the reason, not dropped)
- [/] Golden conversations: scripted multi-turn dialogues with full state assertions (`GoldenConversationTests`; nothing to inject — no clock, no ambient RNG, so a fixed salt is the whole seed)
- [/] Persona lint as a CI gate (shadowing failures block merge)

## Phase 4 — Chat advanced

### Embedding tier ([03-stack.md](docs/03-stack.md#data))

- [/] Pick the embedding model — `all-MiniLM-L6-v2`, fp32 `onnx/model.onnx` (~90 MB), 384-dim, mean-pooled + L2-normalized. **Not quantized**: every published int8 variant of this class targets AVX2/AVX512/ARM64 and the J2900 is SSE4.2-only, so quantizing would be slower, not faster. Fetched by `scripts/fetch-model.sh` (gitignored, `MODEL_PATH` volume)
- [/] ONNX Runtime lazy singleton session in `Sonarr.Infrastructure` (`OnnxTextEmbedder`; missing model files are non-fatal — matching degrades to lexical-only)
- [~] Benchmark: 4.3 ms/embed on the dev box (i7, `IntraOpNumThreads = 2`), inside the 10–50 ms budget with headroom for the J2900 being several times slower. Re-measure on the J2900 itself at the September move
- [/] Semantic matcher: runs only when lexical score is below threshold; never overrides a confident lexical match (`EmbeddingSemanticMatcher`, floor 0.62, rescue score capped just over `LexicalThreshold`; a rescued intent still clears its own guards)
- [/] `chat.intent_embedding` cache keyed by content hash; rebuilt only when the persona file changes (`SemanticIntentIndex` + `SemanticWarmup`; unchanged examples cost nothing, removed ones are pruned)
- [/] `chat.episode.embedding vector(384)` + ivfflat index (`EpisodeConfiguration`, `vector_cosine_ops`, lists=100)
- [/] Backfill job for legacy episode embeddings (batch, minutes) — `EpisodeEmbedder`, 32 rows per batch. Not just legacy: the turn path writes episodes unembedded on purpose, so this is the only thing that ever fills the column
- [/] Callback retrieval: pgvector top-K episode, relevance-gated (`CallbackRetriever`, cosine ≥ 0.55, ≥ 8 turns old; the seeded odds are drawn *before* the lookup so the turns that would discard a tail never pay for the query)
- [/] Authored `examples:` on the intents most likely to be paraphrased (emotions, social, questions, hostility, memory-recall). Capture-driven intents (`SET_NAME`, `SET_FAV`) deliberately have none — a rescue carries no captures and their templates need them

### Relationship & memory features

- [/] Relationship tiers (stranger → … → inner_circle) with tier-gated guards in intents — six tiers in `sonarr.yaml`, thresholds pulled inside the `Registers.Min/Max` clamp (the old ladder topped out at `min_trust: 30`, which trust clamped at 20 could never reach). `persona/intents/tiers.yaml` is the first authored use of `min_tier`/`max_tier`: warm/cold pairs rather than guards on the originals, because the pinned-behavior tests match against `MatchContext.Empty` where `TierId` is null and `min_tier` fails closed
- [/] Authored tier-up moment — `ChatEngine.MarkTierChange` compares the derived tier before/after this turn's affect and appends a line from `tier_up_<id>`; once per tier per person via the persisted fired-log under a synthetic `tier:<id>` key, which is also what keeps demotions quiet
- [/] Assigned nicknames — tier-triggered, pool-drawn, stable per user, stored — drawn once at a tier crossing when no `name` slot exists, from `assigned_nickname`; surfaced to templates through `ConversationState.RenderSlots` rather than written into the slots payload, so the column stays the single home
- [/] `chat.fact` confidence: reinforce on repeat mention → hedging behavior when low — the reinforce half was already in `PersonRepository.UpsertFactAsync` (0.6 initial, +0.15 per repeat, a changed value supersedes rather than overwrites); hedging is `ReplyComposer.Hedged`, which wraps a shaky *value* in an authored `fact_hedge` line instead of pairing every recall pool with an unsure variant, so one pool covers every line that ever substitutes a remembered slot. The threshold (`ChatPipeline.HedgeBelowConfidence = 0.7`) sits between the initial value and one reinforcement, and the comparison happens in the adapter — the engine receives `TurnInput.ShakySlots`, a set of names, so nothing database-shaped crosses into `Sonarr.Elaine`. No slots means no query
- [/] `chat.relationship_event` trajectory queries → `#trend#` ("almost tolerable this week") — `ChatIntrospection.TrendAsync` sums the stored trust deltas over 7 days and appends `trend_up`/`trend_down` to the tier line, so "you're a regular" and "and it's getting worse" can both be true. Summed deltas rather than a level comparison because a delta is movement she caused — decay is not something you did. Below `TrendThreshold` (1.0, roughly one earned moment) the week is flat and gets no line: a sentence about no movement is worse than no sentence
- [/] Multi-day grudge decay — the mechanism was already in place (`ClockSignals.StepsPerHourAway = 1` → `TurnInput.ExtraDecaySteps` → `Registers.Decay(root, 1 + steps)`), so this was a matter of proving the numbers actually behave: with grudge at 0.02/turn a night away is noise, a week measurably cools it, and `MaxExtraDecaySteps = 720` (~30 days) keeps a year away from wiping a nemesis clean. Pinned at both levels — `ChatEngineTests` for the engine arithmetic, `ChatPipelineTests` for the clock wiring, since the pipeline is the only place a real elapsed time turns into a step count. `AbsenceTier` is still derived and unread; the "long time no see" pool it exists for is authored persona work, not code
- [/] Favorites / least-favorites, taking sides, rivalry commentary from trust ordering — `IPersonRepository.GetTrustRankedUsersAsync` orders one guild by trust and returns **ids only**, since another user's registers are theirs (docs/06); raw parameterised SQL casting `(registers->>'trust')::float8` because the column goes through the jsonb serialize-to-text converter and LINQ would otherwise load the whole guild to sort it. `ChatIntrospection.StandingAsync` appends `standing_top`/`standing_bottom` after the tier and trend lines, and only for the extremes — "you're fourth" is a leaderboard and she doesn't hand out numbers. That is also the only rivalry commentary that survives the privacy rule: the line is about *your* position and never names anyone else. `StandingThreshold = 3.0` means somebody she feels nothing about costs no query at all (pinned by `FakePersonRepository.TrustRankReads`), and `MinRanked = 2` because being first of one is not a ranking
- [/] `chat.stance` registry + `stance_agreement` — she remembers whose side you took. The schema, entities, EF config and migration all shipped in `20260727121712_Initial`, and the opinions themselves were already authored in `persona/stances.yaml`; what was missing was any code that read or wrote them, so this is wiring, not machinery. **The pool is the join key**: `stances.yaml` says pineapple_pizza is argued from `social_food` and the FOOD intent draws from `social_food`, so a turn that drew that pool put that opinion on the table — nothing is authored twice and a new topic intent inherits its stance for free (`PersonaGraph.StancesByPool`). "Which opinion did she just voice" is then answered by the already-persisted `FiredLog`: `ChatStances.Taken` looks only at intents whose fired turn equals the pre-turn `state.Turn`, i.e. her immediately previous reply, because agreeing two topics later is agreeing with whatever she said last. No new state, no new migration. `chat.stance` is upserted from the persona on the write path inside the caller's transaction rather than synced by a startup service — an agreement without its opinion is an FK violation, and a reworded opinion self-corrects the next time it comes up. Last word wins per topic: changing your mind replaces the row, since docs/04 says "whose side you took", singular. Affect is fondness ±(1.0/-0.5), not trust — siding with her is charming, not evidence about you, and the AGREE intent's own authored `affect:` block already covers plain agreement. Fell out of the audit: `joke_dad` had 20 authored lines and no intent that could fire them, so the `dad_jokes` stance was an opinion she could never be caught holding — new `DADJOKE` intent (regex-only; a bare `pun` keyword would eat half of JOKE), pinned by a test that every stance's pool is reachable
- [/] `/opinion` — embeds only the topic centroid of recent messages, discards it after; hits the stance registry. `ChatOpinions` takes the last 15 message texts (each cut at 300 chars — a wall of text is still one contribution), embeds them in one batch, averages and renormalises into a centroid, and scores it against the embedded stance topic labels (`topic.Replace('_', ' ')` *is* the query text, pinned by a test that every authored topic id reads as words). The centroid is a local that goes out of scope on return: nothing about the messages is stored, logged or cached, which is the whole metadata-safety claim from docs/10. The text has to be read at the Discord module layer because the Redis ring buffer is deliberately metadata-only (docs/05: author, timestamp, mentioned-her — no content), so `/opinion` calls `GetMessagesAsync` itself and hands the application layer a plain `IReadOnlyList<string>`, which also keeps `ChatOpinions` testable without Discord. `TopicFloor = 0.35`, well below `CallbackRetriever.RelevanceFloor = 0.55`, because this compares a whole conversation to a two-word label rather than sentence to sentence and the same subject scores lower. No match is not an error: she falls back to the already-authored-but-unreferenced `neutral_opinion` pool, which is a real answer, and the same fallback covers a missing model, a stance pointing at a nonexistent pool, and an empty channel. Seeded per topic, so her take on crypto is the same take every time you ask. First consumer of `GetStanceAgreementsAsync`: when your row for that topic exists, one of two new pools (`opinion_you_agreed`/`opinion_you_disagreed`) is appended — only *your* row is ever read, so the public reply cannot leak whose side anybody else took (docs/06). Public rather than ephemeral, since a take on the room is about the room; `DeferAsync` first because embedding a dozen messages is milliseconds on the dev box and uncomfortably close to Discord's 3 s window on the J2900
- [/] Server-event memory: `chat.guild_state.event_log` fed by `PresenceSampler` — `GuildEvent(Kind, Value, At)` and nothing else, pinned by a reflection test: this log is read out loud in a public channel, so a property that could carry a user id would break docs/06 the moment someone added one. The rules live in `GuildEventLog` (pure, in `Sonarr.Domain`) and the repository only loads the row and saves it, which is what makes the behaviour testable — the suite has no database-backed tests and adding one for a comparison would have been the expensive way to check arithmetic. `WithOnlineRecord` returns **null** rather than an unchanged array when the count was not beaten, so a normal sampler pass costs one indexed read and no write; the sampler already skips mid-reconnect, and a second `online <= 0` reject here keeps a zeroed member cache from becoming a record of nobody (which would also make every later sample a "new record"). The old record stays behind the new one — she can say what it was before — capped at 50 entries, because the record before the record before this one is not something she brings up. Malformed or foreign-shaped entries are skipped, not thrown over: a bad log must not cost her a reply. Kept as a jsonb array on the guild's one row rather than a table since it is a handful of entries per guild forever, read whole or not at all. Surfaced on `/serverinfo` as a "Busiest" field (`<t:…:R>`, so Discord renders the age in the reader's own locale) — the authored "last time this many people were online…" line is persona work, and the data it needs is now there
- [/] Mood of the day reseed + seasonal overlay activation — **not** via `DailyTick`, which would be the worse build: a scheduled reseed makes the reply depend on when the tick last ran, so a stored turn can't be replayed, a missed tick leaves her in yesterday, and a restart at 23:59 either double-fires or skips a day. Both signals are already derived from the turn's own instant in `ClockSignals.From` — `DaySeed` (the date, hashed, mixed into the salt) and `Overlays` (`OverlayActivation.Active` over hour/month/day/dow) — which is the same behaviour with no service, no state and no failure mode. What was actually broken was *whose* calendar: `ClockSignals` called `now.ToLocalTime()`, i.e. the container's TZ, so on a UTC container the 3–6 am overlay fired in the Saigon afternoon and the mood turned over mid-morning. Now `From` reads the offset it is handed and the pipeline converts to the **guild's** configured zone (`ConfigKeys.Timezone`, Redis-cached, so one dictionary-shaped read after the gates — an ambient message pays nothing). Guild and never the speaker: an overlay replaces a pool for the whole room, so following whoever is typing would put her in October for one person and not the next. An unset or unresolvable id falls back to UTC rather than throwing — same rule as `ZoneResolver`, and with `InvariantGlobalization` a dev box without tzdata can only ever get that one, which is why the zone-sensitive test asserts against `HasTzData` instead of skipping. `DailyTick`'s remaining duties (streaks, first-message-bonus reset, birthdays, anniversaries) are real scheduled work and stay open at line 314
- [/] Chat engine can recall `social.quote_board` entries — the table shipped in `20260727121712_Initial` with no repository, service or caller, so this is the first code that touches it. Reuses the existing callback seam (`TurnInput.Callback` → `ReplyComposer.Wrap`) rather than adding a second composition path, but **not** the existing pool: every `callback_tail` line claims the quote as hers ("i already told you: …", "my notes say …"), which is right for her own episode and a lie for a board row, where the whole point is who said it. So `TurnInput.Callback` became `RecalledQuote(Quote, Author?)` and a null author selects `callback_tail` while a present one selects the new `quote_board_tail`, whose ten authored lines all name `{$who}` (pinned by a test, because a single line that forgot the author would only misattribute on that one draw, in production). The author stays a raw mention id — resolving a display name would need a gateway lookup in the application layer, and Discord renders `<@id>` anyway; the reply already goes out with `AllowedMentions.None`, so quoting somebody does not ping them. Keyword overlap, not embeddings: a board is tens of rows per guild and its appeal is the exact wording, so `QuoteBoardRecall` reduces the message through the engine's own `Normalizer` to at most 6 content words of 4+ chars and the repository does one `ILIKE ANY` scan (a paraphrase match would surface a quote nobody connects to what was just said). Her own episodes win when both exist — an episode cleared a relevance floor a keyword match cannot promise. Guild-scoped with no exceptions, since a quote board is one server's inside joke; recalling it is only acceptable at all because docs/06 counts a saved quote as data its author consented to. Rides the existing 1-in-2 `WantsCallback` draw, so a turn that would discard a tail still pays for no lookup, and fails open like every other recall. `/quote save` and `/quote random` are the commands that fill the board and stay open at line 306
- [/] Retention: `chat.episode` capped at newest N per user (default 200) + anything referenced by a fact — `PruneAsync` had the cap but not the exception, and its own remark claimed the "referenced by a fact" clause had nothing to read. That was wrong: `chat.fact.learned_at_turn` and `chat.episode.turn` are the same logical clock for the same person, so `(guild_id, user_id, turn)` *is* the join even without an FK, and the clause is now a `NOT EXISTS` against it. Gated on `f.active`, because a superseded fact is kept for trajectory rather than recall and letting a dead one pin an episode forever would make the cap unenforceable — a person who changes their mind often would keep every episode they ever had. One statement, not a read-then-delete: the ranking and the exception belong in the same transaction or a turn landing mid-prune loses a row it just wrote. Driven by `RetentionPruner` at line 336

## Phase 5 — Web & community

### API (Kestrel :5088, [09-web-panels.md](docs/09-web-panels.md#api-surface-bot-process-kestrel-5088))

- [/] ASP.NET Core minimal API hosted in the bot process, plain HTTP (tunnel terminates TLS) — the panel surface is four `MapGroup`s wired in `Program.cs`: `AuthEndpoints`, `MeEndpoints`, `StatusEndpoints`, `AdminEndpoints`. In-process rather than a second service because every route needs the same `IGuildConfigService`, `IFeatureGate` and `DiscordSocketClient` the slash commands use — a separate API process would need either a second DB connection pool or an internal RPC, and both are more moving parts than the J2900 has spare
- [/] CORS locked to `sonarr.hault.io.vn` — one named policy built from `SonarrOptions.PanelBaseUrl` (`WithOrigins` + `AllowCredentials`, `Content-Type` and `X-CSRF-Token` only). The origin comes from config rather than a constant so the dev panel on localhost works without a code change, and prod cannot accidentally ship a wildcard: `AllowCredentials` and `AllowAnyOrigin` throw at startup together
- [/] CSRF double-submit token required on every admin write — readable `sonarr_csrf` cookie echoed into `X-CSRF-Token`, compared with `CryptographicOperations.FixedTimeEquals`. Double-submit rather than a server-side token store because `SameSite=Lax` already blocks the cross-site form POST; the header only has to cover what Lax does not, and there is nothing to store or expire. Enforced on every `/api/admin` write, on `logout-all`, and on both `/api/me` deletes
- [/] Migration — `web`: login_token, session, audit — landed in Migration 1
- [/] `POST /api/auth/request-token` — always 202, neutral response (no user enumeration) — throttled, unknown handle, closed DMs and a delivered code all leave by the same door, and the DM result is deliberately discarded. Ambiguous handles resolve to *nobody*: `core.member.username` is a per-guild cache and is not unique, so `FindUserIdByUsernameAsync` returns null when two rows disagree — DMing the wrong person a login code is worse than a failed login
- [/] Token: 8 chars, unambiguous alphabet (no 0/O/1/I), CSPRNG, SHA-256 hashed at rest, single-use, 10 min — `WebAuthRules`, pure statics so the arithmetic is tested without a web server (`WebAuthRulesTests`). Single-use is settled by the database, not by the read: `ConsumeTokenAsync` puts `AND NOT used` in the WHERE of an `ExecuteUpdate`, so two simultaneous verifies race and exactly one wins (same pattern as `TicketRepository.CloseAsync`). `Normalize` forgives case, `-`, `_` and spaces, because the code is retyped out of a DM by a human
- [/] Rate limits: 3 requests / 15 min per **target username** and per **source IP** (`rl:login:*`) — both windows are consumed **before** the username lookup, so probing handles that do not exist still costs quota. The other order makes misses free, which is the only order an enumerator cares about. Fails closed (a Redis outage blocks logins rather than opening the gate) — the one place in the codebase where the cache does not fail open, and `ICooldownStore` says so
- [/] `LoginTokenSender` — DM the code, record the hash — cache-then-REST user lookup so a member missing from the socket cache still gets the DM, and 50007 (DMs closed) is caught and logged rather than surfaced. `Body` is a static so the wording is assertable; the raw token exists only in that message and in the requesting browser
- [/] `POST /api/auth/verify` — max 5 attempts per token, then the token dies — the counter is keyed **per user** (`rl:login:verify:{user}`, 10 min), not per submitted code: counting per code would let an attacker walk the keyspace by never repeating a guess. Exhaustion deletes the outstanding token, so the 429 means "ask for a new code" rather than "guess again". Kept in Redis rather than a column because the count is only meaningful while the token lives
- [/] Session: 256-bit random id hashed at rest, cookie `HttpOnly; Secure; SameSite=Lax`, 24 h / 90 d remember-me, sliding renewal — the id is lowercase hex rather than base64url, so the cookie value never needs escaping. Remember-me is **derived** from the window (`expires - created > 7 days` can only be the 90 d variant) instead of stored, which avoids a column for a boolean the two lifetimes already encode. Renewal only fires past half-life, so a page view is not a row write — and it returns null for an already-expired session, because a renewal helper that hands a fresh window to a dead session is one missed guard from being a resurrection bug (caught by a test, not by review)
- [/] `POST /api/auth/logout` and `logout-all` ("log out everywhere") — logout always 204: finding nothing already achieved what the caller wanted. The mirror is dropped **before** the row is revoked; the reverse order would leave a revoked session working if the second call failed. `logout-all` requires a fresh session read plus CSRF — it is the "someone has my cookie" button, so it must not trust the cache it exists to invalidate
- [/] `web:session:{hash}` Redis mirror for fast validation; Postgres is the authority; revocation checked in DB on sensitive routes — `AuthenticateAsync(requireFresh)` is the switch. The mirror can never outlive expiry (its TTL *is* the row expiry) but it can outlive a revocation, so admin routes and both deletes pass `true`. A fresh read that finds a revoked row also drops the stale mirror, so the cached path stops lying afterwards — asserted in `WebAuthServiceTests`
- [/] Admin routes: user id checked against the allow-list per request, not the cached session — `AdminAllowList` is consulted on every `AuthenticateAsync`, so `PanelUser.IsAdmin` is never read from a cookie or a mirror. The list is env-sourced (`ADMIN_USER_IDS`) rather than a Postgres table, because docs/04 defines no admin table and adding one for a two-entry env var is a migration to maintain for nothing. Marked `[/]`: the *per-request* half is done, the *in-Postgres* half is deliberately not, and the upgrade path is a `web.admin` table behind the same type when the list stops fitting in an env var
- [/] `GET /api/me`, `/api/me/data`, `/api/me/export` — `/me` is the session probe (id, admin flag, expiry); `/me/data` and `/me/export` are the same `IUserDataRepository.ExportAsync` payload, once as JSON and once as a download. One repository rather than a read through each slice's own: the my-data page *is* docs/06's table, so the query set and the deletion set are the same list read twice, and splitting them across nine repositories is how the page and the doc drift apart. Snowflakes go out as strings — JSON numbers lose precision in JavaScript
- [/] `DELETE /api/me/chat-memory`, `/api/me/everything` (confirmation + cooling-off, honest note about backups) — both need a fresh session, CSRF, and the literal word `DELETE` in the body; both return per-table row counts plus `BackupNotice`, which says outright that a nightly copy may exist for up to 7 days. `mod.case` survives `/everything` on purpose (docs/06: a warning history a user can erase is not a warning history) and the response names the tables it touched rather than leaving the omission to be noticed. Chat-memory drops the `chat.person` row last, so tier, registers, nickname and the fired log reset with it — she genuinely forgets
- [/] `GET /api/status` — public-safe blob, no auth — `ISelfTest.Last` for the dependency checks plus the `web:live_status` blob, passed through as a `JsonNode` so the page reads one object. Status is `unknown` (not `ok`) before the first probe run, because a bot that has been up four seconds has verified nothing. No channel names, no requester names, no guild names — counts, states, and track titles the guild is already hearing out loud
- [/] `GET/PUT /api/admin/*` — config, flags, cases, stats, audit; writes go through the same Application services — config through `IGuildConfigService`, flags through `IFeatureGate`, cases through `IModCaseRepository`, audit through `IWebAuthRepository`. The panel therefore cannot validate config differently from `/config set`, and a rejected value comes back as the service's own message. Three gates in order: fresh session read, allow list, CSRF on writes. 401 without a session cookie and 403 with one, so a logged-in non-admin is told they lack access instead of being bounced to the login page
- [/] `web.audit` row for every panel action — `IWebAuthService.AuditAsync` writes actor, session hash, guild, action, target and a JSON detail blob, truncating action to 64 and target to 256 rather than letting the insert fail. Called by every admin write and by both self-deletes; `web.audit` is itself excluded from the deletion set, since for a self-delete the actor is also the subject and the row is the only trace that a wipe happened
- [/] `StatusPagePusher` — `web:live_status` computed at most once per 5 s regardless of visitors — a `BackgroundService` on a 5 s `PeriodicTimer`, so the cost is fixed no matter how many status pages are open. The key's TTL is also 5 s, which makes a dead pusher show "unknown" rather than a latency number from an hour ago. A push failure warns and keeps the loop alive

### Next.js panels (`web/`)

- [/] App Router + TypeScript scaffold, dark theme, Sonarr branding only — Next 16.2.12 / React 19.2.4, App Router, no `src/`, no Tailwind. One `globals.css` of plain CSS variables instead: the panel is a dozen pages of tables and forms, which is under the weight class where a utility framework or a component library pays for itself. Every foreground/background pair in the palette clears WCAG AA at body size and focus rings are restyled, never removed. `/api/*` is a same-origin rewrite to Kestrel (`next.config.ts`), so the session cookie needs no CORS and no second origin has to be trusted. Server components bypass that rewrite and call Kestrel directly, forwarding the HttpOnly cookie by hand

The failure wording never distinguishes "no such account" from "DMs closed": the API answers 202 either way and a page that guessed would undo that, so the help box covers both causes at once and is the explicit docs/09 ask. A 429 on verify drops back to the handle stage so a wrong code cannot be ground down. The bar is `role="img"` with an `aria-label`, and the real information ("N XP to the next level") is a sentence underneath in prose: the bar is decoration, and a page that puts the only copy of a number inside a CSS width has hidden it. Memberships, levels, facts, an eight-tile counts grid, sessions, and the export link. This is the one endpoint whose snowflakes arrive as JSON numbers, so the ids from it are only ever used to join rows (levels/facts → a guild name via a local `Map`) and never rendered — past 2^53 they are not exactly representable in JavaScript

Only ever about the person asking: there is no route that renders this for someone else and the admin panel deliberately does not get one (docs/06). `ForgetButton` DELETEs one predicate, `encodeURIComponent`'d because a predicate is a path segment holding whatever she wrote down

Votes read as words, not a colour or a bare arrow glyph

The `BackupNotice` from the response is shown verbatim: the panel does not get to paraphrase how long a copy of someone's data survives. Logging out everywhere needs no typed confirmation, since it destroys access and not data
- [/] Admin: Status (gateway, Lavalink, DB/Redis, uptime, heartbeats, queues) — the one page that fetches its endpoint directly rather than through `apiGet`, because `/api/status` is the unauthenticated blob: there is nothing here an admin sees that a visitor could not. - [/] Admin: Config editor with validation + export/import — a row per key with its kind, and a plain text field for every kind regardless. Validation lives in the same `IGuildConfigService` `/config set` uses and its message is rendered as-is: a second rule set in the browser is a second thing to keep in step, and it would disagree eventually. A guild's config is a few dozen keys already listed on one page, so the export is copy-paste and the import is typing — a bespoke file format plus a parser plus per-key failure reporting is real code whose only customer would be moving config between guilds, which has not been asked for. ### Community features

- [/] Migration — `social`: quote_board, capsule, event, event_rsvp, ticket — landed in Migration 1
- [/] `/quote save` (+ context menu) / `/quote random` — `QuoteModule`: `Save quote` context menu on the outer class (a context command has no subcommand path, so it cannot sit inside the `[Group]`), `save`/`random`/`delete` in the nested `[Group("quote")]`. The board is one of docs/06's explicit-consent storage paths, so saving is always a command and never automatic. Confirmations are public, not ephemeral — an ephemeral reply would hide from the quoted person that their line was stored. `AllowedMentions.None` + `Format.Sanitize` everywhere, so being on the board is not a notification. `/quote delete` goes past the two commands asked for because docs/06 gives the quoted person the right to take their own words down; ownership (`SavedBy` or `AuthorId`) lives in the `WHERE` clause, so a guessed id matches nothing instead of removing somebody else's row. `random` uses `ORDER BY random()` — cheap on a board of tens of rows behind the `(guild_id, author_id)` index; ponytail marker records the `TABLESAMPLE` upgrade past a few thousand.
- [/] `/capsule write when message` — delivery via `core.job` — `CapsuleService` (Application, behind `ICapsuleService` because `ZoneResolver` is internal) + `CapsuleJobHandler` + `[Group("capsule")]`. Two rows per capsule: the text in `social.capsule`, the timing in `core.job` with a payload that carries only `capsule_id` + `user_id`. A reminder-style payload-only design would have been less code, but a capsule can sit for a year and docs/06 requires `/privacy` and forget-me to reach the text — a job payload is not a place anybody looks. The capsule row is written before the job, so the losing half is an unopened row somebody can still find rather than a job pointing at nothing that fails three times and wakes a human. Recurring phrases are refused (`/remind` is the repeating one) and anything inside an hour is refused too, since the parser's floor is seconds and that would make this a slow `/say`. Caps: 2048 chars (the column) and 10 unopened per person per guild — these are the only user-authored rows that outlive a membership. `delivered_at` is stamped **after** a successful post, not claimed before it: stamping first makes a failed send permanent, while the remaining narrow window only ever double-posts, and the `delivered_at IS NULL` clause in the `UPDATE` makes a late retry a no-op. Confirmation is ephemeral (a capsule is a surprise), and on open the author is the only mention.
- [/] `/event create|list|cancel` — native Discord events + opt-in role pings — `EventService` (behind `IEventService`, same internal-`ZoneResolver` reason as capsules) + `EventRepository` + `EventModule`. The commands split by audience rather than by noun: `/events` and the RSVP buttons sit on the outer class so anyone can read the schedule and answer, while `create`/`cancel` live in a nested `[Group("event")]` carrying `[DefaultMemberPermissions(ManageEvents)]`. That attribute is only a hint Discord can be told to ignore, so `cancel` re-checks `GuildPermissions.ManageEvents` itself and the service takes staffness as a flag — permissions are Discord's to answer, ownership is the row's. The native scheduled event is a best-effort mirror created *after* the RSVP post: if Discord refuses it (External events need an end time and a location, both invented here — channel name, +2h) the event still exists and the buttons still work, and the failure is an ephemeral followup rather than a lost command. `ping_role` is the opt-in half: going grants it, maybe/no take it back, and the module refuses `@everyone` and managed roles up front and checks its own hierarchy before touching anyone's roles. Recurring phrases are refused — a series needs its own cancel semantics and a native event per occurrence, which is not what was asked. Caps: 100/1000 chars (the columns, and Discord's title limit), 10 upcoming per creator per guild, 10 min minimum lead, a year maximum. Counts for `/events` come from one grouped query for the whole page rather than one per row.
- [/] `/ticket` — private thread with mods; close button saves a transcript — `TicketService` (a plain class, no interface: it takes nothing internal, same call as `ShipMeter`) + `TicketRepository` + `TicketModule`. The thread is a **private** thread with `invitable: false`, so only staff can pull anyone else in, and a one-week auto-archive is the safety net for tickets nobody closes. Validation is split from persistence — `CheckAsync` runs the topic and the 3-open-per-person cap *before* the thread exists, because the row stores the thread id and so cannot be written first, and creating a thread only to refuse the ticket would leave litter in the channel. The transcript is read back off the thread at close time (last 500 messages) rather than mirrored into Postgres as it happens: docs/06 stores what a user explicitly saves, and a live ticket is not that. It is posted as a `.txt` to `ConfigKeys.LogChannel` and only the jump URL goes in `transcript_ref` — the text lives where the mod log already lives, under whatever retention that channel has. A failed transcript (no log channel, no permission) is deliberately non-fatal: the ticket still closes, because trapping an open thread over a logging problem is the worse failure. The `status = open` test sits in the `WHERE` of the `UPDATE`, so two people hitting the button post one transcript and the second click answers "already closed". Closing is opener-or-`ManageMessages` and the handler re-reads the ticket by thread id and cross-checks the button's id against it, so a member pulled into the thread cannot close it and a stale button cannot act on someone else's ticket.
- [/] `/ship user_a user_b` — deterministic seed from the id pair, no table — `ShipMeter` (Application) + `ShipModule`. FNV-1a over the *sorted* id pair, so `/ship a b` and `/ship b a` are the same question, and the answer never re-rolls — a changing number would make it obvious it means nothing. Guild-independent on purpose: two people are the same two people in every server they share, and a per-guild number invites shopping for a better one. The line is drawn seeded on the percentage rather than the turn, so the verdict is as stable as the arithmetic it claims to be. Three authored bands in `introspection.yaml` (`ship_low/mid/high`, third person — anyone can ship anyone). Public reply with `AllowedMentions.None`: the joke is for the room, but being shipped is not a notification. Nothing stored, no table, as specified.
- [/] `/anniversary` — auto-announced join anniversaries + command shows yours — `MilestoneService` (behind `IMilestoneService`, internal-`ZoneResolver` again) + `MilestoneModule`, no new columns: `core.member.first_seen_at` already carries the date, so the only new repository method is `GetJoinAnniversariesAsync` (month+day match, same shape as `GetBirthdaysAsync`). Nothing is scheduled and nothing is stored — the announcer asks "who joined on this month+day in an earlier year" against the guild-local date, so there is no per-member state to keep in sync and a missed day costs one greeting instead of leaving a stale row. Year zero is skipped: "happy 0th" on somebody's first day is a bug, not a welcome, and `WelcomeFlow` already said hello. The command is public with `AllowedMentions.None` (a join date is not private, being asked about is not a notification) and shows the next date and the days until it, so somebody who checks in March learns when to come back.
- [/] Birthday feature (opt-in `core.member.birthday`, month+day) — `/birthday set month day [year]` / `/birthday clear` in a nested group; `core.member.birthday` and `SetBirthdayAsync`/`GetBirthdaysAsync` already existed and were unused. Month+day is the stored fact; the optional year is only kept when it is plausible (13–120 on the day, per Discord's own floor) and is used for nothing but `/anniversary`'s own reply — the public greeting never prints an age, because the age is the part that is nobody's business. Yearless birthdays go in under sentinel year 4, a leap year, so 29 February is storable without claiming a birth year; in a common year `ObservesLeapDay` widens the query so those members are greeted on 1 March rather than silently skipped for three years out of four. All arithmetic sits in `MilestoneRules` (Domain, pure, clock-free) and is driven directly by tests; the service is a query plus a persona line. Confirmations are ephemeral — the date of birth is the disclosure, the greeting is the public part.
- [/] `SeasonRoller` — month boundary: close season, write results, announce top chatter, open next — `SeasonRules` (Domain, pure) + `SeasonService` (behind `ISeasonService`, internal-`ZoneResolver` again) + `SeasonRoller`, no schema change. **XP is never reset**: `levels.progress.xp` is a lifetime total, so "earned this season" is derived as `total − sum(previous season xp_earned)` (`SeasonStanding`) — closing a season takes away nobody's level, needs no per-season XP table and no snapshot row at open time, and a close that fails leaves the next roll able to catch up. Clamped at zero, because an admin XP reset can leave a total below what earlier seasons already counted and a negative "earned" would sort a wiped member onto the podium. A season is a **calendar month in the guild's own timezone**, not configured policy — nothing to set up, nothing to get wrong, and the first season is opened lazily on the first roll rather than backfilled for guilds already in the database. Close and results are one transaction with `status = active` in the `WHERE`, so two rollers racing means the loser writes nothing instead of a second set of standings; the next season is opened *after* the close commits, and the "nothing open" branch picks up a roller that died between the two. Members who earned nothing are left out of `season_result` entirely (docs/06 — a result means taking part, and the row would outlive the membership for no reason). Announcement is best-effort and after the commit: freezing the month is the durable part, and a season left open because the announce channel was deleted would keep counting into next month. Polled hourly (the boundary is a different instant per guild, DST moves it) plus one pass on start, so a bot that was down over a boundary rolls immediately. `/leaderboard` and its autocomplete now name seasons by month, since that is what they are.
- [/] `DailyTick` — streaks, first-message-bonus reset, birthdays, anniversaries, mood reseed, overlay check — one `BackgroundService`, but only the greetings are actually in it. The streak and the first-message bonus are **derived on read** (`StreakRules.CurrentDays` compares `streak_last_day` against today; the bonus compares `first_msg_bonus_day`) — a nightly sweep over every member row to write down what a comparison already answers is work that can be skipped, and skipping it means a night the bot is down costs nothing. Mood reseed and the overlay check are excluded by line 253. That leaves the one duty that must happen *at a time*: greetings at guild-local 09:00, found by polling every 15 min rather than sleeping to a computed instant, since "the next 09:00" differs per guild and DST moves it. The day flag is an in-memory dictionary (ponytail: a Redis day-key is the upgrade, and a restart re-greeting is the failure mode) and it is stamped **before** posting — a repeat every 15 minutes is worse than a missed greeting. Output goes to `ConfigKeys.AnnounceChannel`, which doubles as the per-guild opt-in without growing the closed key catalog. Mentions are batched at 10 per message; `Compose`/`Group` are public statics so the message shape is testable without waiting for 09:00.
- [/] Streak display in `/rank` — `StreakRules.CurrentDays(stored, lastDay, today)` in `GetCardAsync`, plus `LevelsModule.Streak` for the wording (0 reads as "none", not "0 days" — a broken streak is a state, not a count). The comparison is done in **UTC**, matching the day `XpOnMessage` stamps on the row: reading in the guild's zone would look nicer and be wrong, because west of UTC the stored day can already be "tomorrow" by that clock and a member who just spoke would be shown a streak of zero.

## Cross-cutting (must hold at every phase)

### Privacy & data ([06-data-and-privacy.md](docs/06-data-and-privacy.md))

- [/] No general message-content logging — counts and timestamps only — audited as a test, not as a paragraph: `PrivacyAuditTests` reflects over every entity in `Sonarr.Domain.Entities` and fails on any `string` column this audit has not accounted for, in both directions (an undeclared column *and* a declaration for a column that no longer exists — an unverifiable justification is as bad as a missing one). Of the 50 columns, exactly six hold user-authored text and each is named with its consent path. The three handlers that see every message store nothing of it: `XpOnMessage` never touches `Content`, `AntiSpamHandler` passes it to a service that keeps only a SHA-256 of the normalised form in Redis under a TTL, and `ChatOnMessage` hands it to the engine. No log statement anywhere in `src/` interpolates message text
- [/] Content stored only when: you talk to Sonarr, you explicitly save it, or a mod action captures context — the six user-text columns are exactly those three cases and nothing else: `chat.fact.value` (told to her while addressed, deletable per-fact), `social.quote_board.content` and `social.capsule.message` (saved by a command, never automatically), `social.event.name`/`description` (the creator's own), and `mod.case.reason` (a moderator typed it). `chat.episode.quote` looks like a fourth and is not — `ChatPipeline` stores `result.Text`, which is *her* line, and `ChatPipelineTests.A_turn_only_stores_her_own_line_as_an_episode` is the test that keeps it that way. A ticket transcript is the one bulk capture and it deliberately does not land in Postgres: it is read off the thread at close time and posted to the log channel, with only a jump URL in `transcript_ref`
- [/] Chat engine learns **only** from mention/reply — never mines the channel — structural rather than checked: `ChatPipeline.HandleAsync` returns `NotAddressed` before any repository call when `Addressed` is false, so an ambient message cannot reach a fact write even by accident, and `An_ambient_message_gets_no_reply_but_still_feeds_the_ring_buffer` asserts zero writes. The ring buffer it does feed is Redis-only, TTL'd, and holds `(userId, at, addressed)` — no text. `IsAddressed` counts a mention or a reply to one of her own messages; `@everyone` deliberately does not, or every announcement would summon her
- [/] DM content never stored except the login token we sent (hashed) — nothing in `src/` handles a DM at all: there is no `IDMChannel`, `SocketDMChannel` or `IPrivateChannel` reference in the whole solution, and every message handler drops anything whose channel is not a `SocketTextChannel` before the first service call. So a DM has no path to a service, let alone to a table. The only DM the bot *sends* is the login code, stored as `web.login_token.token_hash` — SHA-256, single-use, 10-minute expiry, raw value never persisted
- [/] No third-party/outbound data sharing (list stays empty by design) — one `HttpClient` exists in the entire solution (`LavalinkProbe`), it hits the Lavalink on loopback, and the Application and Domain assemblies have no HTTP dependency at all — `ArchitectureTests` already forbids transport packages there. Nothing calls an analytics, telemetry or model API: the embedder is ONNX in-process, which is the reason docs/03 chose it. The list is empty because there is no code that could put anything on it
- [/] `/privacy`, the panel "My data" page, and this doc must never disagree — single source — enforced from both ends. `PrivacyNoticeTests` reads `docs/06-data-and-privacy.md` off disk and asserts the notice and the doc still state the same hard rules and the same retention numbers, so a doc edit the command does not follow fails the build. The panel page cannot drift for a different reason: it renders `IUserDataRepository.ExportAsync`, the same payload `/api/me/export` downloads and the same list `DeleteEverythingAsync` removes — the query set and the deletion set are one list read twice rather than nine repositories that would eventually disagree
- [/] Timezone + birthday are opt-in via command only — nothing infers either. The only writers are `IMemberRepository.SetTimezoneAsync` and `SetBirthdayAsync`, reached from exactly one command each (`/timezone`, `/birthday set`), and both accept null to clear. No gateway handler and no job writes them, so a member who never runs the command has both columns null forever
- [/] Mod cases are not self-service deletable (audit integrity) — `DeleteEverythingAsync` names 17 tables and `mod.case` is not among them, deliberately, and the response body says so rather than leaving the omission to be noticed. The panel shows `modCases` in its counts grid for the same reason: a member can see a warning history they cannot erase, which is the honest version. Erasing one is a guild-owner decision through `/case delete`, and that writes its own audit row
- [/] User panel queries scoped to session `user_id` in **every** query — the subject always comes from `AuthenticateAsync` and never from the request. `PrivacyAuditTests.No_user_panel_route_takes_a_user_id` reflects over both `/api/me` endpoint classes and fails if any handler even *accepts* a parameter with "user" in its name — these are minimal-API delegates, so anything bindable is a route value, a query string or a body, all attacker-controlled. `guildId` is the one thing a page does choose, and the panel checks it against the caller's own membership list before sending it (`web/lib/guilds.ts#selectedGuild`) rather than trusting the URL
- [/] Web app has no DB credentials and no Discord token — `PrivacyAuditTests.The_web_app_reads_no_secret_from_its_environment` scans every `.ts`/`.tsx` under `web/` and asserts the set of `process.env.*` reads is exactly `["SONARR_API_URL"]`. A second env var fails the test, which is the point: the way this breaks is somebody adding a `DATABASE_URL` for one convenient query. The compose service passes that one variable and nothing else, and the panel's only reachable surface is Kestrel — every read goes through `lib/api.ts`, every write through `lib/client.ts`

### Retention & maintenance

- [/] `RetentionPruner` (04:00): episode caps, dead login tokens/sessions, Redis orphans, stats > 400 d — a plain `BackgroundService` on a daily delay, **not** a `core.job` row like everything else in `JobScheduler`. Durability is the only thing a job row buys, and a missed sweep costs nothing here: every cutoff is computed from "now", so the next run deletes the same rows plus a day's worth. `UntilNextRun` treats 04:00 exactly as *tomorrow*, or a sweep finishing inside the same minute would immediately run again. The episode cap and the row sweep sit in separate try blocks: the cap is the half that keeps the pgvector table searchable, and a failing stats delete must not skip it. Four `ExecuteDeleteAsync` calls rather than one — deliberately not a single transaction, so one wedged table does not roll back the other three, and each filters on an already-indexed column (`expires_at` on both web tables, `hour_bucket`, `day`). **Redis needs no sweep at all**: every key the bot writes carries a TTL, so docs/08's "expired Redis orphans" is handled by construction, which is what line 338's audit exists to keep true. `SweepAsync` is public so the tests drive a sweep without waiting for 04:00 — same pattern as `JobScheduler.PollOnceAsync`
- [/] `stats.activity_sample` aggregated hourly, kept 400 days — the aggregation was already structural rather than a job: the table keys on `(guild_id, hour_bucket)` and `PresenceSampler` truncates its 5-minute sample to the hour, so the twelve samples in an hour upsert one row instead of growing the table. That is the cheap half of "aggregated" and it needs no reduce step. The 400-day half is the pruner at line 336, deleting on the indexed `hour_bucket`; at one row per guild per hour, 400 days is under 10 k rows per guild, which is why the window can be that generous
- [/] Redis audit: every key has a TTL; nothing durable lives only in Redis — enforced two ways, neither of them a document someone has to remember to re-read. `RedisCacheBase.WriteAsync` takes the expiry as a **required** parameter and throws on a non-positive one, so a key cannot be written without a TTL at all; and `RedisKeysTests` now reflects over both types in both directions — every builder in `RedisKeys` must have a same-named `CacheTtl` entry, and every `CacheTtl` entry must belong to a live builder. The second direction matters as much as the first: a TTL nobody reads is a policy that has drifted from the key it claims to govern, which is exactly how a key ends up written with an arbitrary literal at the call site. "Nothing durable" is the reference-direction rule already pinned by `ArchitectureTests` plus docs/05's own list — facts, episodes, relationships and jobs are Postgres-only, and `core.job` is the authority precisely so the scheduler survives a flush
- [/] `FLUSHALL` blast-radius test: costs only reset conversations, one music session, panel re-logins — every key family now declares which of docs/05's three permitted costs it is, and a second reflection test fails if any family has no declaration. That pairing is the whole point: asserting the three costs alone would pass forever while somebody quietly adds a fourth. The classifications that needed a decision rather than a glance: the rate limiters are a *reset*, not data loss, since a flush only forgives whoever was mid-window — and `rl:login` fails **closed** while Redis is down, so a flush can never open the DM-token gate; `presence:*` is a reset because `PresenceSampler` re-samples within 5 minutes and `stats.activity_sample` already holds the durable copy; `cfg:*` is a reset because a miss falls through to the guild's Postgres row, costing one uncached read. `web:session` is a mirror of the `web.session` table, so the worst case is the re-login docs/05 already allows

### Backups & ops ([11-deployment.md](docs/11-deployment.md#backups-user-decision-files-on-host-foldered-by-yearmonth))

- [/] `BackupRunner` 03:30 — `pg_dump` → `/root/backups/sonarr/YYYY/MM/sonarr-YYYY-MM-DD.dump` — a timer, not a `core.job` row, for the same reason as `RetentionPruner`: a missed backup costs a day and tomorrow's run needs no memory of today's. 03:30 is deliberately half an hour *before* the 04:00 sweep, so the dump captures the rows the sweep is about to delete rather than the state after. Both run times now come from one `DailySchedule.UntilNextRun`, and `The_dump_runs_before_the_retention_sweep` is the test that keeps that ordering from being reversed by a later edit. It shells out because there is no in-process alternative — only `pg_dump` writes a `pg_restore`-compatible archive, and a restore drill that needs a custom tool is a drill that fails, so `postgresql-client` is now installed in the runtime image and `BackupProbe` goes red at boot if it ever vanishes. **Dropped the `| gzip` docs/11 originally specified**: `--format=custom` is already zlib-compressed, so the pipe would spend J2900 CPU to add roughly nothing and the double extension invites a drill that gunzips first and then wonders why. Both docs updated to match the code rather than the reverse. Credentials are parsed out of `PG_CONNECTION` with `NpgsqlConnectionStringBuilder` and passed as `ArgumentList` entries with the password in `PGPASSWORD` — never on the command line, because `/proc/*/cmdline` is world-readable and this process shares a host with the old bot. Both pipes are drained concurrently with the wait, or a chatty `pg_dump` filling the stderr buffer would deadlock against `WaitForExitAsync`; a 30-minute cap kills the tree if it wedges
- [/] Dump sanity check (non-zero, header check); failure = red line in the log channel — `BackupVerification` is a pure function (`long` + the first bytes → a problem clause or null) so the rules are tested without a disk: under 1 KiB is a truncated write, and the file must start with `PGDMP`, which also catches "someone changed the format flag and the restore drill still says `pg_restore`". The dump is written as `.dump.partial` and **renamed only once it verifies** — the rename is the commit, so a killed `pg_dump` can never leave something that looks like last night's backup, and a file that fails the check is deleted rather than kept where the next prune would count it as a monthly. The red line rides `ISelfTest` rather than posting to the channel directly: docs/08 wants one line on failure, and the self-test already owns that line *and* its change-detection, so a broken backup also shows up in `/status` and cannot become a nightly wall of identical alarms. `BackupProbe` also treats a *successful* backup older than two days as red — a dead timer looks identical to a healthy one otherwise. Before the first run it reports what would stop 03:30 from working at all (no `/backups` mount, no `pg_dump` on PATH) instead of a cheerful green
- [/] Weekly config backup: persona dir + `.env`, `config-` prefix, same tree — Monday, so it lands on a predictable file each week and retention sees one archive per week rather than a drifting date. `TarWriter` + `GZipStream` from the BCL, not a shell-out — nothing here needs `tar`. The `.env` is the interesting half: inside the container there is no such file, the values arrive as environment, so the archive holds an `.env` **reconstructed from the running `SonarrOptions`**. That is the same content and strictly better than copying the host file, because it cannot drift from what actually booted. Written at mode 0600 inside the archive, since it holds the bot token and the Lavalink password and a restore that widens those is a restore that leaks them. A failed config archive logs but does **not** go red: the dump is the backup that matters and the persona directory is in git
- [/] Retention: dailies 30 days, then first-of-month kept 12 months — `BackupRetention.Expired` is pure and the runner deletes exactly what it names, so it can never over-delete. Two decisions the literal wording forced: (1) past the window the survivor is the **earliest file of each calendar month**, not the 1st — a weekly config archive almost never lands on the 1st, so "first-of-month" would have deleted nearly all of them; (2) "earliest" is computed over the whole month rather than over its expired half, or a month straddling the 30-day boundary would keep both the 1st *and* the oldest file still inside the window, which `A_month_straddling_the_boundary_keeps_one_file` pins. Retention is judged per prefix so the two sets cannot prune each other. `Parse` matches the known extensions rather than splitting on the first dot, which is what makes a `.partial` invisible to the prune — the earlier version happily parsed one, and the test caught it. Anything unrecognised parses to null and is therefore left alone: a stray file in the backup tree is not deleted by a rule written without it in mind
- [/] Restore drill documented in-repo; tested once before cutover, then quarterly — [deploy/RESTORE.md](deploy/RESTORE.md): pick a dump, `pg_restore` into a throwaway `pgvector/pgvector:pg17` on 127.0.0.1:55432, verify extensions/row counts/embeddings/freshness against live, boot a bot at it, tear down, log the result in the table at the bottom. Updated in this pass to match what the runner now writes — no `gzip -dc`, `pg_restore --list` as the strongest check short of a real restore, and an explicit "never restore a `.partial`". The scratch bot deliberately uses a **different** Discord token: a second gateway connection on the same bot user fights the live one. Teardown `shred`s the temporary `.env`. The drill itself is still untested against a real dump — that needs the CT, so it belongs with cutover rather than here
- [/] Document the single-disk caveat; weekly `rsync` to the old CT once the J2900 lands — stated in docs/11 next to the retention rules and repeated at the foot of RESTORE.md, where someone mid-restore will actually read it: backups on the same disk as the database protect against bugs and bad deploys, not disk death, and real redundancy starts when the J2900 lands and the CT demotes to an rsync target (checklist 363)
- [ ] Never touch `lavalink.service`, the yt-cipher container, or `/root/lavalink/*`
